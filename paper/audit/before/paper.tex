\begin{abstract}
Many embedded and desktop applications search thousands rather than millions of vectors. At that scale, fixed costs, memory duplication, filter preparation, and the first query after a mutation can matter more than asymptotic index complexity. We study \qenlo{}, a Rust vector store with one canonical record model and optional exact CPU, portable WGPU, and PyTorch execution. The target regime is \(10^3\) to \(10^5\) vectors, dimensions 128--768, query batches 1--64, and filtered as well as unfiltered search. All comparisons time a completed host call through ordered identifiers and distances; correctness is checked independently against an FP64 oracle.

On an RTX 4090, exact WGPU search over 100k 768-dimensional vectors reaches 0.897 ms P95 for batch one and \(k=1\), versus 9.409 ms for the native CPU and 14.800 ms for FAISS Flat. PyTorch CUDA is faster at 0.671 ms. With batch eight, \(k=64\), and 10\% eligibility, WGPU reaches 0.896 ms, FAISS Flat 3.055 ms, and PyTorch CUDA 0.384 ms. Every corrected row has oracle recall 1.0. The lane-minimum selector optimization is not a universal win: across 12 qualified before/after WGPU pairs, it wins five and loses seven. In-place GPU append and live-mask updates avoid a rebuild in the measured mutation cells, while reopen still rebuilds resident state. The campaign retains unavailable hardware, three Chroma correctness disqualifications, two invalid-harness rows, and four pre-fix admission failures. Final known cloud spend was \$0.9401. These results support a small-collection portable-GPU path and explicit resource admission. They do not establish mobile performance or a universally fastest database.
\end{abstract}

\section{Introduction}
The usual vector-search story starts with scale: as \(\N\) grows, scan cost grows, so an approximate index becomes attractive. That is true, but it skips the regime many applications actually ship. A phone, desktop tool, local retrieval feature, or per-user collection often holds between 1k and 100k vectors. Here a search implementation pays for predicate evaluation, dispatch, synchronization, top-\(k\) selection, and result conversion on every call. A fast kernel can still lose once those costs are included.

This paper asks a narrower question: how should one durable vector-store core execute exact filtered search over small collections when CPU, portable GPU, and an application's existing tensor runtime are available? Resource use is part of the answer. We report latency with process RSS, \qenlo-owned accelerator allocations, scratch, transfers, build time, and post-mutation preparation where the harness can attribute them. We do not collapse these quantities into one efficiency score.

The study makes four contributions. First, it defines one correctness and persistence boundary across embedded and accelerated builds. Second, it evaluates a portable WGSL top-\(k\) selector in which each lane retains its minimum and only the winning lane rescans its stripe. Third, it measures in-place mutation updates and a generation-bound optional tensor index. Fourth, it publishes a failure-preserving matrix over synthetic and retained real embeddings, with Chroma, FAISS Flat, NumPy, USearch, and PyTorch comparisons.

The main finding is mixed. Portable GPU execution is useful at 100k vectors, including batch-one calls, but the selector change regresses more paired cells than it improves. PyTorch CUDA wins the two corrected 768-dimensional cells, while it carries a larger runtime and is not the durable source of truth. That result argues for measured deployment profiles, not one backend everywhere.

\section{System and contracts}
\subsection{One canonical core, two profiles}
\qenlo{} stores normalized FP32 vectors, unsigned public identifiers, user and timestamp metadata, tombstones, and a monotonically increasing generation in one canonical Rust store. Distance is cosine distance. Results use one total order: ascending distance, then ascending identifier. Atomic batches publish only after validation and durable staging; stale derived plans fail closed.

The embedded profile keeps CPU exact search, bounded scratch, portable snapshots, and the language bridge needed by the host application. GPU support is an optional build feature. The accelerated profile adds WGPU, richer diagnostics, bulk ingestion, and optional PyTorch integration. These profiles select features around the same records and persistence semantics; they are not separate databases.

Execution policy is explicit. CPU mode never initializes a GPU. Required-GPU mode fails on initialization, capacity, or device loss instead of falling back. Automatic mode reports the requested and actual route plus any fallback reason. A load budget covers the canonical rows, an aligned CPU scan view, metadata-index allowance, and durable-write admission. GPU admission covers resident vectors, identifiers, masks or eligible-row lists, selector scratch, query data, and readback staging.

\subsection{Portable exact GPU execution}
The WGPU backend uses one WGSL implementation across Vulkan, Metal, and DX12. Vectors stay resident when the generation is prepared. A query scores every eligible row, produces bounded candidates, and returns host-visible identifiers and distances. The evaluated selector candidate retained each lane's current minimum and rescanned only the lane that supplied the previous winner. Empty eligibility, partial workgroups, maximum \(k\), and distance/identifier ties used the same ordering as the CPU path. Because the campaign found seven regressions in 12 qualified pairs, the final source keeps the simpler full-rescan selector.

This optimization reduces redundant stripe scans, but it adds lane state and changes synchronization behavior. We therefore keep it only as a measured implementation change. Table~\ref{tab:before-after} shows that it is not uniformly faster.

\subsection{Mutation and tensor integration}
Adds append resident rows when capacity permits. Deletes update a live mask. Each derived update is bound to the canonical generation, so a search cannot combine vectors from one generation with liveness from another. A full rebuild remains the bounded fallback when capacity, layout, or device state prevents an incremental update.

The Python \texttt{TorchIndex} is an optional immutable tensor view. It accepts contiguous arrays or tensors, supports CPU, CUDA, and MPS device selection, executes query batches as matrix operations, and returns tensors without a JSON round trip. A canonical collection snapshot carries its generation and filter identity. A mutation makes the snapshot stale; callers must reject or rebuild it. PyTorch remains a desktop extra and is imported lazily. It is not required by mobile artifacts and is not a second durable store.

\section{Experimental method}
\subsection{Workloads and engines}
The common sweep covers 1k, 10k, and 100k rows; dimensions 128 and 384; batches one and 16; and unfiltered or 1\%-eligible predicates. A reference RTX 4090 adds 5k, 25k, and 50k cells, batch 64, \(k\in\{1,10,64\}\), compound filters, lifecycle measurements, and a retained 100k-by-384 AG News embedding fixture. A corrected supplement covers 100k-by-768 at batch one, \(k=1\), unfiltered and batch eight, \(k=64\), 10\% eligible.

The engines are the frozen pre-change \qenlo{} CPU/WGPU revision, the revised native CPU/WGPU implementation, NumPy, FAISS Flat, PyTorch CPU/CUDA, Chroma HNSW, and USearch where the harness supports the workload. We do not equate approximate and exhaustive rows. Chroma and USearch qualify only when independent FP64-oracle recall meets the predeclared target.

\subsection{Timing and qualification}
Completed-call time starts before the host search call and ends after ordered identifiers and distances are visible to the host. Device-resident PyTorch timing is reported separately and is never substituted for completed-call latency. Corpus load, index construction, and warmup are outside the query interval. Engine order rotates, raw samples are retained, and reported P50/P95/P99 values are lower medians of per-run nearest-rank percentiles.

Native rows contain 24--192 completed calls depending on batch size. External replay rows use three complete repetitions. That is enough to expose large effects and failures, but too little for narrow confidence intervals. We report exact sample counts and avoid significance claims.

The corrected 768-dimensional supplement uses source archive SHA-256 \texttt{bb195fed...eb19}. Earlier current/native rows use \texttt{730c0500...e3}; the frozen baseline archive is \texttt{f37e744c...a45d}. The working tree was dirty, so the archive hashes, not the Git commit alone, identify executable source.

\subsection{Campaign controls}
The Runpod controller checked spend since midnight in Asia/Calcutta, reserved \$1, calculated worst-case exposure before each creation, recorded pod identifiers immediately, and started an independent deletion watchdog. Ten primary configurations were attempted across RTX 2000 Ada, L4, A40, RTX 3090/4090, and A6000 families. Unavailable offers remain in the matrix instead of being replaced. Deeper work ran only on a reference RTX 4090. At completion, the API returned zero pods and final known daily spend was \$0.9400778694. Billing lag remains possible; no campaign volume or disk was retained.

The resource result is less flattering. In the unfiltered cell, WGPU reports 311.2 MB of \qenlo-owned accelerator allocation and a 1.204 GB process RSS high-water mark, versus 665.8 MB RSS for CPU. The call uploads 403,136 bytes and reads back 48 bytes. With batch eight and \(k=64\), owned accelerator allocation is 314.9 MB, upload is 517,120 bytes, and readback is 65,792 bytes. These are different scopes: process RSS is a process-wide high-water mark, while accelerator allocation is backend-attributable. We do not add or divide them into one score.

Phase timing explains the second cell. Median device scoring is 0.072 ms, selection is 0.613 ms, backend execution is 0.826 ms, and completed-call P95 is 0.896 ms. Selection, synchronization, and readback dominate arithmetic. This is the case for a hierarchical selector only if its extra scratch and dispatch can beat that 0.613 ms in a matched run.

The acceptance rule was to retain complexity only when measured benefit justifies it. These data do not justify making the lane-minimum selector an unconditional replacement. The implementation therefore reverts the revised selector and retains its measurements as a negative result. A future bounded hierarchical merge or dispatch rule needs matched evidence on the losing cells before it enters the durable path.

\subsection{Mutation and reopen cost}
On the RTX 4090 reference workload, add-one then search reaches 0.598 ms P95; delete-one then search reaches 0.631 ms. Small add and delete batches reach 0.740 and 0.819 ms. Rebuild fraction is zero in all four cells, and deletion checks pass. Mutation publication itself costs about 22 ms P95 in these durable runs. Reopen is different: first search takes 101.296 ms and rebuild fraction is one. Incremental resident updates solve the warm mutation case; they do not eliminate restart preparation.

\subsection{Chroma target and qualification}
In the seven qualified paired cells, revised WGPU is faster than Chroma HNSW at the completed-call boundary; ratios range from 3.700$\times$ to 3233.136$\times$. This is a scoped result, not a product-wide claim. Chroma includes its own API and filtering path, uses approximate HNSW, and three attempted Chroma configurations fail the predeclared recall gate before held-out timing: two at \texttt{ef\_search}=128 and one at 512. The disqualified rows remain visible. The result supports ``Qenlo beat Chroma in these qualified cells,'' not ``Qenlo is the fastest database.''

\section{Failures and negative results}
The campaign matrix has 182 rows: 131 completed, 42 unavailable primary-configuration rows, seven engine failures, and two invalid-harness rows. Four of the seven engine failures are 100k-by-768 admission rejections from the pre-fix source. The benchmark accepted a 2 GiB vector budget but constructed the in-memory collection with the 512 MiB default storage admission. The final supplement adds an explicit in-memory constructor option and forwards the benchmark budget. A regression test proves that the supplied limit governs atomic batches. We retain both the failures and the corrected-source hash.

The first 768-dimensional supplement also passed internal cell labels to the benchmark as positional arguments. No benchmark executed. Those two rows are marked \texttt{invalid\_harness}; they are not counted as performance failures. This distinction matters because a green controller exit only proves that the script reached its end. Artifact status, hashes, summaries, and oracle qualification determine whether a measurement is usable.

\section{Deployment implications}
For embedded builds, CPU exact search remains the default because it has no accelerator residency, driver initialization, or desktop tensor dependency. A mobile application may enable WGPU only after measuring completed-call latency and peak memory on the physical device. This campaign has no Android or iOS measurements, so it cannot select a mobile default.

For accelerated desktop builds, exact WGPU is a reasonable measured option near 100k rows. PyTorch CUDA is faster in the two 768-dimensional cells, but bundling PyTorch only for search adds installation and runtime cost. The tensor path makes sense when the application already owns a compatible embedding runtime or needs tensor-native batches. FAISS Flat remains a useful independent exhaustive baseline. Chroma remains an approximate database comparison with different persistence and filtering boundaries.

The simplest current policy is explicit backend selection plus transparent automatic fallback. The matrix is too small for a learned router. Fixed choices should use collection size, dimension, batch, eligible fraction, and device class; any selector-specific rule must be validated on the actual adapter.

\section{Related work}
FAISS provides optimized exhaustive and approximate CPU/GPU search \citep{johnson2019billion,douze2024faiss}. HNSW trades recall for graph-traversal work \citep{malkov2020hnsw}. DiskANN and SPANN address much larger storage-aware regimes \citep{subramanya2019diskann,chen2021spann}. Filtered-DiskANN and ACORN modify graph access under predicates \citep{gollapudi2023filtered,patel2024acorn}. Recent filtered-ANN studies show that selectivity, correlation, and implementation change the best method \citep{iff2026fanns,shi2025unified,amanbayev2026systems}.

Our contribution is not a new asymptotic nearest-neighbor algorithm. It is a measured implementation boundary for exact search over small collections: one canonical durable store, bounded derived state, portable GPU selection, completed-call timing, mutation behavior, and explicit failure accounting.

\section{Limitations}
The current cloud evidence covers NVIDIA Vulkan hosts, not Metal, DX12, Android, iOS, or phone Linux. Ten primary configurations were attempted, but only the available RTX 2000 Ada, A40, and RTX 4090 hosts produced measurements. External engines use three repetitions in the corrected supplement, which limits uncertainty estimates. Synthetic vectors dominate the matrix; the retained AG News fixture covers one 384-dimensional workload. Filters are controlled but do not span realistic vector/metadata correlation. There is no power measurement.

Process RSS is a high-water mark and cannot be assigned cleanly to one library. GPU allocation is \qenlo-owned rather than physical VRAM telemetry. The WGPU and PyTorch paths use different runtime stacks. Chroma's database/API boundary is broader than a raw matrix operation. The paper reports those boundaries instead of treating every row as interchangeable.

The release is also incomplete as a platform claim until Apple device/simulator artifacts and Android packages are built in CI and exercised on physical devices. Cloud NVIDIA results cannot fill that gap.

\section{Conclusion}
Small collections are large enough for accelerator execution to matter and small enough for fixed costs to decide the result. On one RTX 4090, \qenlo{} WGPU completes exact 100k-by-768 search in about 0.9 ms P95 and beats the tested CPU, NumPy, and FAISS Flat paths. PyTorch CUDA is faster in both corrected 768-dimensional cells. The lane-minimum selector itself wins five and loses seven qualified baseline pairs, so it is not ready as an unconditional optimization.

The practical result is a narrower product direction. Keep one canonical Rust store. Make CPU, required GPU, automatic fallback, and tensor execution explicit. Admit memory before the first query. Update resident state by generation after mutations. Publish every failure beside the wins. The remaining claim is deliberately plain: Qenlo now has credible small-collection acceleration evidence on the tested desktop GPUs. Mobile performance and a universal fastest-database claim remain unproven.

\begin{center}\begin{minipage}{0.88\textwidth}\small\noindent\textbf{Abstract.} GPU latency comparisons usually treat a kernel's speed as a property of its code and hardware. For latency-bound work it also depends on the performance state the driver selects, which may depend on the load the work itself imposes. We study two GPU paths of an exact filtered vector-search engine that return identical top-$k$ results: a \emph{light} path whose work scales with the $E$ eligible rows, and a \emph{heavy} path that scans all $N$ rows. Across fresh processes on an RTX 4050 Laptop, RTX 4090s on six cloud hosts and an H100, the heavy kernel's device time reproduced within 1\% on one machine and within 7\% across hosts, while the light kernel's varied up to $4.2\times$ on one machine and $4.6\times$ across hosts with the same GPU model. On the laptop, locking the clocks removed the light kernel's variation (spread from $2.8\times$ to $1.00\times$), and a low lock reproduced the slow mode. Clocks could not be locked on the cloud hosts, so the cross-host differences rest on indirect evidence. GPU power state can shape kernel benchmarks of light work, and device time should be reported separately from end-to-end latency. Protocols, raw data and telemetry are released.\end{minipage}\end{center}\vspace{1.2em}]

\section{Introduction}\label{sec:intro}
A retrieval call in an agent or RAG pipeline is often small: one query, a metadata filter that leaves a few thousand candidates, $k=10$. Whether such a call should run on a GPU, and in which form, is usually decided by measuring it. We find that for light calls the measurement depends on more than the implementation and the hardware. It also depends on the GPU's performance state, which the driver sets in response to load, including the load of the call being measured.

This study began with a reproducibility asymmetry. Our system has two GPU execution paths for exact filtered top-$k$ search that return identical results. A \emph{light} path uploads the list of $E$ eligible rows and does device work proportional to $E$. A \emph{heavy} path evaluates the filter inside the kernel and does device work proportional to all $N$ rows, up to $1{,}000\times$ more at our most selective filter. When we re-ran one query cell in fresh processes, the heavy path's top-$k$ kernel time reproduced to three decimal places. The light path's moved between modes $2.4\times$ apart (Section~\ref{sec:repro}), and its fast mode coincided with higher GPU clocks. On other hosts with the same GPU model, the light kernel's median was up to $3.8\times$ faster while the heavy kernel's differed by at most 4\%.

The direct test is to lock the clock. That needs administrator rights, which we had on the laptop but not inside the cloud containers, so on the cloud hosts we raise the clock instead. A separate process, the \emph{heater}, keeps the GPU lightly busy. If the variation came only from contention, the heater could only slow every path down. If it came from power state, the heater should speed up work that was running below its attainable clock and slow down only work that was already at boost. In preregistered experiments on three GPU types (Figure~\ref{fig:central}c, Section~\ref{sec:intervention}), every GPU showed the second pattern at the device level. With the heater, the share of light-kernel runs more than $1.5\times$ slower than their best fell from 52\% to 0\% on the laptop, from 28\% to 16\% on the RTX 4090s and from 11\% to 0\% on the H100. The heavy kernel never got faster. End-to-end latency did not show the predicted speed-up, because the heater also competes for the GPU and, on some hosts, for the CPU. We report both.

\paragraph{Contributions.}
\begin{itemize}
\item \textbf{A reproducibility asymmetry.} For identical results, the more work-efficient GPU kernel is the less reproducible one. It varies up to $4.2\times$ on one machine and $4.6\times$ across same-model hosts, while a kernel doing up to $1{,}000\times$ more work reproduces within 1\% on a machine and 7\% across hosts (Section~\ref{sec:repro}).
\item \textbf{Evidence for a power-state account.} Continuous telemetry links the variation to driver-selected performance states. A preregistered intervention, which can only add contention and includes a negative control, makes the light kernel's slow runs rarer on three GPU types and never speeds up the heavy kernel (Sections~\ref{sec:states}--\ref{sec:intervention}). The end-to-end prediction failed, and we report it as failed. On the laptop, where clocks could be locked, a locked-clock experiment confirmed the account: the light kernel's spread across processes vanished at fixed clocks (Section~\ref{sec:lock}).
\item \textbf{Consequences for evaluation.} With unlocked clocks, the measured device-time advantage of the light path over the heavy path for the same cell ranges from $3.4\times$ to $12.6\times$ across our hosts, and kernel-level results from one machine do not carry over to another with the same GPU. We give reporting rules (Section~\ref{sec:consequences}).
\end{itemize}

\section{Limitations}\label{sec:limitations}
\emph{One system, one workload family.} Both paths come from one engine with a simple selection kernel. Heavier or better-tuned kernels, such as FAISS or cuVS selection, may run in different states, so we do not expect these magnitudes to carry over. \emph{Clock locking on one machine.} Locking clocks was possible only on the laptop; it was refused in the cloud containers. The cross-host variation therefore rests on the heater, which also loads the host and is not a clean GPU-only perturbation. The locked-clock test covers one GPU, one driver and one operating system. \emph{Telemetry.} \texttt{nvidia-smi} samples every 50\,ms and only part of the time \citep{yang2023parttime}; clocks are reported for active samples of a whole process, including warm-up. \emph{Small $n$.} Five blocks on the laptop, five RTX 4090 pods (one block each, on five different hosts) and three H100 blocks give coarse intervals, and host differences between pods widen them. One pod was replaced before analysis because its host CPU was about $14\times$ slower on a single-threaded test; its partial block is archived but excluded from the tables. \emph{Host coupling.} On the laptop and the H100 the heater also changed host-side timings, so end-to-end effects there cannot be attributed to the GPU clock alone. \emph{API.} All runs use Vulkan through WGPU; CUDA runtimes may be managed differently. \emph{Driver versions.} 616.56 (Windows) and 570.195--580.173 (Linux).

\section{Conclusion}\label{sec:conclusion}
On the GPUs we tested, the faster implementation of a light query was also the one whose kernel time varied most between processes and machines. The variation tracked the clock the driver chose. On the laptop, fixing the clock removed it. Raising the GPU's load on every host made the light kernel's slow runs rarer at the device level, though not faster end to end. The heavy path does more work, holds a high clock, and therefore looks more stable, and its gap to the light path looks smaller than it would at equal clocks. Benchmarks of retrieval kernels, and the routers and design decisions built on them, should record the GPU's power state, replicate across it, and report device time separately from end-to-end latency.

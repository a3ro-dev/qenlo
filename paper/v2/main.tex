\section{Introduction}\label{sec:intro}
GPUs drop to lower clocks when they are lightly loaded. Kernel benchmarking practice knows this, and locks clocks or warms the device up before timing \citep{oliaro2026fastkernels,chu2026operatorprofiler}. Application-level benchmarks usually do neither. They compare implementations at the driver's default clocks, and the implementations being compared can load the GPU very differently. A work-efficient kernel that leaves the GPU mostly idle can be clocked down; a wasteful one that keeps it busy is not. The measured gap between them then partly reflects the power state each one induced. We report one case of this and test it.

The case comes from Qenlo, an embedded vector store with two GPU paths for exact filtered top-$k$ search that return identical results. A \emph{light} path uploads the list of $E$ eligible rows and does device work proportional to $E$. A \emph{heavy} path evaluates the filter inside the kernel and scans all $N$ rows; its selection kernel makes $k$ passes over all $N$ scores in one workgroup. The heavy path is not a competitive baseline. We keep it because it computes the same answer while holding the GPU at boost, which makes it a load contrast and a negative control. At $E=10{,}000$ eligible rows out of $N=100{,}000$, the light path is faster than both the heavy path and our CPU scan on the laptop and the RTX 4090 pods (Appendix Table~\ref{tab:crossover}), so this is a regime where an application would choose it. There its kernel time varied $1.4\times$ between fresh processes on the laptop and $4.6\times$ across five RTX 4090 cloud pods, while the heavy kernel's varied by at most 1\% on one machine and 7\% across the pods (Section~\ref{sec:repro}). At smaller $E$ the CPU wins and the light path's spread matters less in practice, although it is as large.

The direct test is to lock the clock. That needs administrator rights, which we had on the laptop. There, in an experiment whose protocol and predictions were committed to version control before its first run (Section~\ref{sec:lock}), locking the SM and memory clocks at boost removed the light kernel's spread across processes, and locking them at the light path's observed low state reproduced its slow mode. One of its five predictions failed: locked at boost, the light kernel took 32--50\% less time than the best unlocked median, outside the 15\% we had predicted.

Inside the cloud containers clocks could not be locked, so there we tried to raise the clock instead. A separate process, the \emph{heater}, keeps the GPU lightly busy. If the variation came only from contention, the heater could only slow every path down; if it came from power state, it should speed up work that was running below its attainable clock. At the device level that is what we saw on all three GPU types: the share of light-kernel runs more than $1.5\times$ slower than their best fell from 52\% to 0\% on the laptop, 28\% to 16\% on the RTX 4090 pods and 11\% to 0\% on the H100, and the heavy kernel never got faster (Figure~\ref{fig:central}c, Section~\ref{sec:intervention}). The heater is a crude instrument. It also uses host CPU, it slowed host-side work by 40--48\% on the H100 pod, and the end-to-end speed-up we had planned to see did not appear on any GPU. Its protocols were written before the data but committed only afterwards (Appendix~\ref{app:protocols}). We treat the cross-host account as supported by telemetry and the heater, not as tested.

\paragraph{Why a small engine.} Everything here ran on one laptop plus about US\$6 of rented GPU time. That was possible because Qenlo is small enough to instrument end to end: device timestamps on every call, a fresh process per measurement, continuous clock telemetry, and two code paths with identical outputs that load the GPU differently. With those in place, finding the effect, testing it by locking clocks and releasing every sample took days. We think small, fully instrumented engines are a cheap way to do this kind of systems measurement, and we offer Qenlo as one.

\paragraph{Contributions.}
\begin{itemize}
\item \textbf{An observation in one engine.} For identical results, Qenlo's work-efficient GPU path is the less reproducible one. Its kernel time varies up to $4.2\times$ between fresh processes on one machine and $4.6\times$ across five same-model cloud hosts, while the heavy path's varies by at most 1\% on one machine and 7\% across those hosts (Section~\ref{sec:repro}).
\item \textbf{A locked-clock test on one laptop.} With its protocol committed before the data, locking the clocks removed the light kernel's variation and a low lock reproduced the slow mode (Section~\ref{sec:lock}).
\item \textbf{Weaker evidence across hosts.} Telemetry and the heater are consistent with the same account on RTX 4090 and H100 hosts; the planned end-to-end prediction failed, and we report it as failed (Sections~\ref{sec:states}--\ref{sec:intervention}).
\item \textbf{Reporting rules and data.} We give rules for benchmarking latency-bound GPU work (Section~\ref{sec:consequences}) and release protocols, raw samples and telemetry.
\end{itemize}

\section{Limitations}\label{sec:limitations}
\emph{One engine, one kernel pair.} Both paths come from Qenlo, with a simple hand-written WGSL selection kernel, and the heavy path is deliberately naive. Tuned library kernels such as FAISS or cuVS may load the GPU differently and run in different states; testing them, and more hosts per GPU model, needs compute we did not have. We do not expect these magnitudes to carry over. \emph{Clock locking on one machine.} Locking was possible only on the laptop and was refused in the cloud containers, so the cross-host account rests on telemetry and the heater, which also loads the host. The locked-clock test covers one GPU, one driver and one operating system. \emph{Laptop platform.} The laptop uses hybrid graphics (Optimus): the display runs on the Intel iGPU and the RTX 4050 renders nothing else during the runs. It ran on AC power under the Windows ``Balanced'' plan; we did not test other plans. \emph{Telemetry.} \texttt{nvidia-smi} samples every 50\,ms and only part of the time \citep{yang2023parttime}; clocks are reported for active samples of a whole process, including warm-up. \emph{Small $n$ and confounding.} Five blocks on the laptop, five RTX 4090 pods with one block each on five different hosts, and three H100 blocks. On the pods, host and process variance cannot be separated, and with three to five blocks the bootstrap intervals are descriptive at best. The pods also span two driver branches. One pod was replaced before analysis because its host CPU was about $14\times$ slower on a single-threaded test; its partial block is archived but excluded. \emph{Host coupling.} On the laptop and the H100 the heater also changed host-side timings, so end-to-end effects there cannot be attributed to the GPU clock alone. \emph{API.} All runs use Vulkan through WGPU; CUDA runtimes may be managed differently. \emph{Driver versions.} 616.56 (Windows) and 570.195--580.173 (Linux).

\section{Conclusion}\label{sec:conclusion}
In Qenlo, the faster GPU path for a light query was also the one whose kernel time varied most between processes and machines, and the variation tracked the clock the driver chose. On the laptop, fixing the clock removed it. On the cloud hosts we could only raise the GPU's load, which made the light kernel's slow runs rarer at the device level but did not make calls faster end to end. The heavy path holds a high clock, so it looks more stable than it would at equal clocks, and its gap to the light path looks smaller. For benchmarks of light GPU work, we would record the power state, replicate across fresh processes, and report device time separately from end-to-end latency. A small engine with this much instrumentation should find similar effects in other kernels for little money, which is the use we have in mind for it.

\section*{Reproducibility}
Each experiment's protocol and predictions were written before its data were collected, but only the locked-clock protocol was committed to version control before its data; the others were committed the same evening, after collection (Appendix~\ref{app:protocols}).

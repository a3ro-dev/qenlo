\begin{abstract}
GPU latency comparisons usually treat a kernel's speed as a property of its code and its hardware. For latency-bound work, the speed also depends on the performance state the driver selects, and the driver may select it partly from the load the work itself imposes. We study two GPU paths of an exact filtered vector-search engine that return identical top-$k$ results. The \emph{light} path does work proportional to the $E$ eligible rows; the \emph{heavy} path scans all $N$ rows. We ran fresh processes on three GPU models: an RTX 4050 Laptop, RTX 4090s on six cloud hosts, and an H100. The heavy top-$k$ kernel's device time reproduced within 1\% across processes on one machine and within 7\% across hosts. The light kernel's device time varied by up to $4.2\times$ on one machine and $4.6\times$ across hosts with the same GPU model. In 50\,ms telemetry, the driver ran the light path at lower clocks (on the laptop, 585\,MHz SM and 810\,MHz memory; on the H100, 645\,MHz SM) while the heavy path stayed at boost. In preregistered experiments, a separate process that kept the GPU lightly busy reduced the share of light-kernel runs more than $1.5\times$ slower than their best from 52\% to 0\% on the laptop, from 28\% to 16\% on the RTX 4090s and from 11\% to 0\% on the H100, while the heavy kernel stayed the same or slowed down. Contention alone would slow both paths, so this pattern fits a power-state account better. The preregistered end-to-end speed-up did not appear: the added load also competes for the GPU and the host, and full query latency changed little or got worse. GPU power state can therefore shape kernel-level benchmarks of light work, and device time should be reported separately from end-to-end latency. Our data do not show that power state is the only cause of the latency differences. Protocols, raw per-call data and telemetry are released.
\end{abstract}

\section{Introduction}\label{sec:intro}
A retrieval call in an agent or RAG pipeline is often small: one query, a metadata filter that leaves a few thousand candidates, $k=10$. Whether such a call should run on a GPU, and in which form, is usually decided by measuring it. We find that for light calls the measurement depends on more than the implementation and the hardware. It also depends on the GPU's performance state, which the driver sets in response to load, including the load of the call being measured.

This study began with a reproducibility asymmetry. Our system has two GPU execution paths for exact filtered top-$k$ search that return identical results. A \emph{light} path uploads the list of $E$ eligible rows and does device work proportional to $E$. A \emph{heavy} path evaluates the filter inside the kernel and does device work proportional to all $N$ rows, up to $1{,}000\times$ more at our most selective filter. When we re-ran one query cell in fresh processes, the heavy path's top-$k$ kernel time reproduced to three decimal places. The light path's moved between modes $2.4\times$ apart (Section~\ref{sec:repro}), and its fast mode coincided with higher GPU clocks. On other hosts with the same GPU model, the light kernel's median was up to $3.8\times$ faster while the heavy kernel's differed by at most 4\%.

The direct test would be to lock the clock, but that needs administrator rights on consumer machines and was refused inside cloud containers. We raise the clock instead. A separate process, the \emph{heater}, keeps the GPU lightly busy. If the variation came only from contention, the heater could only slow every path down. If it came from power state, the heater should speed up work that was running below its attainable clock and slow down only work that was already at boost. In preregistered experiments on three GPU types (Figure~\ref{fig:central}c, Section~\ref{sec:intervention}), every GPU showed the second pattern at the device level. With the heater, the share of light-kernel runs more than $1.5\times$ slower than their best fell from 52\% to 0\% on the laptop, from 28\% to 16\% on the RTX 4090s and from 11\% to 0\% on the H100. The heavy kernel never got faster. End-to-end latency did not show the predicted speed-up, because the heater also competes for the GPU and, on some hosts, for the CPU. We report both.

\paragraph{Contributions.}
\begin{itemize}
\item \textbf{A reproducibility asymmetry.} For identical results, the more work-efficient GPU kernel is the less reproducible one. It varies up to $4.2\times$ on one machine and $4.6\times$ across same-model hosts, while a kernel doing up to $1{,}000\times$ more work reproduces within 1\% on a machine and 7\% across hosts (Section~\ref{sec:repro}).
\item \textbf{Evidence for a power-state account.} Continuous telemetry links the variation to driver-selected performance states. A preregistered intervention, which can only add contention and includes a negative control, makes the light kernel's slow runs rarer on three GPU types and never speeds up the heavy kernel (Sections~\ref{sec:states}--\ref{sec:intervention}). The end-to-end prediction failed, and we report it as failed.
\item \textbf{Consequences for evaluation.} With unlocked clocks, the measured device-time advantage of the light path over the heavy path for the same cell ranges from $3.4\times$ to $12.6\times$ across our hosts, and kernel-level results from one machine do not carry over to another with the same GPU. We give reporting rules (Section~\ref{sec:consequences}).
\end{itemize}

\section{Limitations}\label{sec:limitations}
\emph{One system, one workload family.} Both paths come from one engine with a simple selection kernel. Heavier or better-tuned kernels, such as FAISS or cuVS selection, may run in different states, so we do not expect these magnitudes to carry over. \emph{No clock locking.} The most direct test, running both paths at identical locked clocks, was unavailable: it needs administrator rights on the laptop and was refused in the cloud containers. The heater is an indirect substitute, and because it also loads the host it is not a clean GPU-only perturbation. \emph{Telemetry.} \texttt{nvidia-smi} samples every 50\,ms and only part of the time \citep{yang2023parttime}; clocks are reported for active samples of a whole process, including warm-up. \emph{Small $n$.} Five blocks on the laptop, five RTX 4090 pods (one block each, on five different hosts) and three H100 blocks give coarse intervals, and host differences between pods widen them. One pod was replaced before analysis because its host CPU was about $14\times$ slower on a single-threaded test; its partial block is archived but excluded from the tables. \emph{Host coupling.} On the laptop and the H100 the heater also changed host-side timings, so end-to-end effects there cannot be attributed to the GPU clock alone. \emph{API.} All runs use Vulkan through WGPU; CUDA runtimes may be managed differently. \emph{Driver versions.} 616.56 (Windows) and 570.195--580.173 (Linux).

\section{Conclusion}\label{sec:conclusion}
On the GPUs we tested, the faster implementation of a light query was also the one whose kernel time varied most between processes and machines. The variation tracked the clock the driver chose, and raising the GPU's load made the light kernel's slow runs rarer at the device level, though not faster end to end. The heavy path does more work, holds a high clock, and therefore looks more stable, and its gap to the light path looks smaller than it would at equal clocks. Benchmarks of retrieval kernels, and the routers and design decisions built on them, should record the GPU's power state, replicate across it, and report device time separately from end-to-end latency.
